# EchoLens Agent 代码注释规范

> 版本：1.0
> 制定日期：2026-08-31
> 适用范围：EchoLens Agent 仓库中的 TypeScript、JavaScript、Shell、配置示例与测试代码

## 1. 规范定位

本规范参考公开的安全编码规范和开源工程实践，并结合 TypeScript、JSDoc/TSDoc 的通用约定进行适配。

本文采用公开实践中较稳定的原则：

- 使用“必须、应、可以”区分规则强度。
- 注释服务于代码维护和安全审查，不追求注释数量。
- 代码、注释和文档必须同步更新。
- 不在代码、日志、错误和注释中泄露敏感信息。
- 优先让代码本身清晰，注释负责解释代码无法直接表达的约束。

规则关键词：

- **必须**：违反后可能导致错误、安全风险或严重维护成本。
- **应**：通常需要遵守，只有明确理由时才可例外。
- **可以**：根据上下文选择，不作为强制审查项。

## 2. 核心原则

### 2.1 注释解释原因，不翻译代码

注释应优先说明：

- 为什么采用当前方案。
- 哪个业务、协议或安全约束要求这样做。
- 哪些看似可简化的逻辑不能删除。
- 当前实现承担了什么风险或兼容性责任。
- 修改这段代码前必须保持什么不变量。

不应逐句复述变量赋值、条件判断或函数名已经表达的内容。

```ts
// 不推荐：把代码翻译成中文。
retryCount += 1; // 重试次数加一

// 推荐：解释这个上限的来源和目的。
// Provider 可能返回 Retry-After；本地上限用于避免单次 Turn 长时间占用执行槽。
retryCount += 1;
```

### 2.2 优先改进代码，再补充注释

当代码需要长篇注释才能理解时，应先考虑：

- 改善命名。
- 拆分函数。
- 提取具有领域含义的类型或常量。
- 降低分支和嵌套复杂度。
- 使用结构化数据代替字符串约定。

注释不能用来掩盖混乱的结构。

### 2.3 注释必须与代码同步

修改受注释约束的代码时，必须同时检查注释是否仍然成立。过期注释比没有注释更危险。

代码审查时，注释应作为变更的一部分检查。无法确认准确性的注释应删除或改写，不能保留“可能已经不对”的描述。

### 2.4 注释应短、准、可验证

注释应使用明确事实，避免以下模糊表达：

- “这里比较特殊”。
- “暂时这样处理”。
- “应该不会出问题”。
- “因为某些原因”。
- “以后再优化”。

应写明具体原因、限制、问题编号或完成条件。

## 3. 必须添加注释的场景

以下场景必须或应添加注释。

### 3.1 安全边界

涉及以下内容时，必须说明信任边界和失败策略：

- 工具输出、MCP 内容或规则文件被视为不可信数据。
- 权限升级、审批、Guardrail 和 deny 优先规则。
- 路径规范化、符号链接、Junction、ADS、UNC 或句柄级校验。
- 凭据读取、脱敏、Token 轮换和日志过滤。
- Gateway 与本地工作区之间的数据边界。
- Shell、Docker、网络代理和外部进程隔离。

```ts
// 工具输出只能作为不可信证据回填，不能进入 System Policy 或改变权限集合。
const contextItem = createToolOutputContextItem(result);
```

安全注释必须描述真实控制措施，不能使用“这里是安全的”作为结论。

### 3.2 不变量和并发约束

以下逻辑应说明必须保持的不变量：

- Event Store 的单写者和递增 `seq`。
- 并行只读工具的结果排序。
- 副作用工具不得与其他写操作交叉。
- Checkpoint 恢复不得重复执行已经完成的工具。
- Abort、Timeout 和 Retry 之间的竞态处理。

```ts
// 完成顺序可以不同，但回填必须按 callIndex 排序，保证 Provider 消息稳定。
results.sort((left, right) => left.callIndex - right.callIndex);
```

### 3.3 协议兼容和外部限制

当实现受外部协议约束时，应说明约束来源或兼容目的，例如：

- Chat Completions 与 Responses 的字段差异。
- SSE 跨网络分片和 CRLF 边界。
- OAuth Device Flow 的轮询间隔与 `slow_down`。
- Provider 不支持并行工具调用或结构化输出时的降级。
- Windows 与 POSIX 路径语义差异。

有公开规范时，应在模块文档或附近注释中附规范名称；不要求每处重复 URL。

### 3.4 非直观算法和正则表达式

复杂算法、状态机、压缩策略和安全相关正则应说明：

- 输入和输出。
- 关键边界条件。
- 复杂度或资源上限。
- 为什么不能采用更直接的实现。

简单、常见且命名清晰的正则不必逐字符解释。

### 3.5 临时兼容方案

临时方案必须关联问题编号或明确移除条件，禁止只写“临时处理”。

```ts
// TODO(#184): Provider 完成 Responses 流式 Usage 支持后删除此兼容分支。
```

## 4. 注释形式

### 4.1 行注释 `//`

用于实现内部的局部约束和决策说明。

```ts
// 恢复操作代表用户显式批准一个新的有界执行片段。
executor.resetBudget();
```

行注释应位于相关代码上方。只有非常短且不会影响阅读时才使用行尾注释。

### 4.2 文档注释 `/** */`

以下导出 API 应使用 TSDoc/JSDoc 文档注释：

- 名称不足以表达契约的公共类型和接口。
- 具有副作用、权限要求或异常语义的公共函数。
- 跨模块复用且调用方式不直观的类。
- Provider、Tool、Session、Gateway 等边界接口。

不要求为每个导出符号机械补齐注释。名称、类型和契约已经清楚时，可以不写。

```ts
/**
 * 从最近的持久化检查点恢复同一 Turn。
 *
 * 已完成的工具结果不会重复执行；本次恢复获得新的有界运行预算。
 * @throws Session 没有检查点或检查点属于其他工作区时抛出错误。
 */
async function resumeSession(): Promise<AgentRunResult> {
  // ...
}
```

### 4.3 块注释 `/* */`

块注释只用于需要连续说明的局部设计，不应用于注释掉大段代码。

废弃代码必须由 Git 保存历史，不能长期以注释形式留在源码中。

### 4.4 文件头注释

默认不添加作者、创建日期、修改记录或版权模板，除非许可证要求。

原因：

- 作者和修改历史由 Git 提供。
- 手工日期容易过期。
- 复制模板会制造无价值噪声。

模块存在重要安全边界、生命周期或协议职责时，可以添加简短模块说明。

## 5. TSDoc/JSDoc 标签

### 5.1 `@param`

只有参数含义、单位、范围或安全要求无法从类型和名称看出时才添加。

```ts
/**
 * @param timeoutMs 请求总时限，包含重试等待时间，必须大于零。
 */
```

禁止写没有信息增量的内容：

```ts
/** @param timeoutMs 超时时间 */
```

### 5.2 `@returns`

返回值存在特殊状态、所有权或降级语义时使用。不要只重复返回类型。

### 5.3 `@throws`

公共 API 会抛出调用方需要处理的错误时使用。稳定错误码优先写错误码和触发条件，不承诺不稳定的错误文本。

### 5.4 `@deprecated`

必须说明替代方案和计划移除版本或条件。

```ts
/**
 * @deprecated 使用 `ModelRouter.resolve()`；旧入口将在 v0.8 删除。
 */
```

## 6. TODO、FIXME 和 HACK

### 6.1 TODO

`TODO` 必须包含可追踪的问题编号或明确负责人，并说明完成条件。

推荐格式：

```ts
// TODO(#issue): 原因；满足什么条件后如何处理。
```

### 6.2 FIXME

`FIXME` 表示已知缺陷，不得作为长期占位。必须关联 Issue，并在合并前评估是否影响安全或数据正确性。

```ts
// FIXME(#231): Resize 后滚动锚点会漂移；合并虚拟列表前保持此保护分支。
```

### 6.3 HACK

原则上不使用 `HACK`。确有外部兼容限制时，必须说明：

- 被兼容的系统或版本。
- 正常方案为什么不可用。
- 移除条件。
- 对应测试位置。

## 7. 语言和格式

- 项目内部注释默认使用简体中文。
- API 名称、协议字段、错误码和代码标识符保留英文原文。
- 中英文之间保持自然空格，例如“解析 Provider 响应”。
- 完整句子使用标点，短标签可以省略句号。
- 注释行应控制长度，复杂说明优先分段，不把整篇设计文档塞进源码。
- 禁止使用侮辱性、情绪化或针对个人的描述。
- 禁止在注释中记录聊天内容、临时调试信息或无关背景。

## 8. 敏感信息规则

代码注释必须遵守与日志相同的秘密管理要求。

禁止写入：

- API Key、Access Token、Refresh Token、Cookie 或 Authorization Header。
- SSH 私钥、密码、真实服务器地址或内部域名。
- 用户隐私数据、真实账号、手机号或邮箱。
- 生产数据库连接信息和内部网络拓扑。
- 可用于绕过审批、限流或权限校验的操作细节。

示例中必须使用明显的占位符：

```ts
const token = '<redacted>';
const endpoint = 'https://example.invalid/v1';
```

发现秘密值时，不能只删除注释；还必须按泄露事件处理并轮换相关凭据。

## 9. 测试代码注释

测试名称应优先表达场景和期望，避免依赖注释解释测试目的。

测试注释适用于：

- 解释难以构造的竞态窗口。
- 标明安全攻击样本的意图。
- 说明 Fixture 为什么故意不符合协议。
- 解释 Windows 或 Provider 特有行为。

```ts
test('相同步骤预算下恢复仍可进入新的执行片段', async () => {
  // 首次运行必须在工具轮次后耗尽预算，才能覆盖真实的 /resume 场景。
});
```

禁止使用 `sleep` 后只写“等待一下”之类注释，应说明等待的事件或竞态条件。

## 10. Agent 项目专项要求

以下模块的注释应重点描述相应责任：


| 模块            | 注释重点                                       |
| --------------- | ---------------------------------------------- |
| Provider Codec  | 协议字段映射、停止原因、流式边界、重试安全性   |
| Context Manager | 稳定前缀、隐私级别、规则优先级、数据与指令分离 |
| Tool Executor   | 权限、审批、副作用、预算、取消和超时           |
| Event Store     | 单写者、顺序、恢复、脱敏和损坏处理             |
| Path Policy     | 规范化、句柄校验、链接与 Windows 特殊路径      |
| Gateway         | 无本地执行权、认证、转发透明性、日志边界       |
| TUI             | 终端列宽、输入状态、滚动锚点和审批交互         |

注释不能替代以下内容：

- Tool Schema。
- 稳定错误码。
- 类型系统约束。
- 自动化测试。
- 审批 UI 和安全策略。

## 11. 代码审查检查表

审查者应检查：

- 注释是否解释了原因、约束或风险，而不是复述代码。
- 注释是否与当前实现一致。
- 安全边界和不变量是否得到说明。
- 是否存在被注释掉的废弃代码。
- TODO/FIXME 是否可追踪且有完成条件。
- 文档注释是否描述副作用、异常和权限要求。
- 是否泄露秘密值、服务器信息或用户数据。
- 注释是否可以通过更好的命名或结构删除。
- 变更代码时是否同步修改了相关注释和测试。

## 12. 推荐示例

### 不推荐

```ts
// 检查是否取消
if (signal.aborted) {
  // 返回取消
  return cancelled();
}
```

### 推荐

```ts
// 在发起 Provider 请求前再次检查，避免取消后仍产生计费请求。
if (signal.aborted) return cancelled();
```

### 不推荐

```ts
// 这里不能并行，会有问题。
await writeFile(path, content);
```

### 推荐

```ts
// 写工具必须串行进入 Event Store，避免审批快照与实际工作区状态漂移。
await writeFile(path, content);
```
